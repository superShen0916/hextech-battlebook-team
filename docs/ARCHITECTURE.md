# 维护架构与改动边界

项目保持一套业务实现、一库、一份静态站源码和一个原发布目标。现有 `.cmd` 是用户入口；`scripts` 的流程入口协调步骤，业务规则与正式校验仍沿用当前实现。

## 构建与发布的职责

| 模块 | 唯一职责 | 修改时要注意 |
| --- | --- | --- |
| `app/project_paths.py` | 数据库、前端、构建和发布目录 | 保留原绝对路径绑定 |
| `scripts/release_inputs.py` | 数据、前端、验收三类内容指纹 | 新数据算法脚本/脚本依赖登记 `DATA_SCRIPTS`；业务模块、评分和配置保持内容检测 |
| `scripts/release_files.py` | 文件内容清单、整树摘要、差异复制与目标完整核对 | 不用大小/mtime代替内容；清单只在当前持锁操作内复用 |
| `scripts/release_reuse.py` | 候选目录组装、三个固定槽位轮换 | 只操作固定候选/上版；保留失败恢复，不新增逐轮目录 |
| `scripts/sync_release.py` | 固定发布目标的校验与同步接口、兼容CLI | 构建和人工流程共用 `synchronize_release`；`--check` 独立读取两侧全量内容 |
| `scripts/build_release.py` | 唯一数据构建链、原门禁、产物确认 | `stages` 同时记录子进程与内部操作耗时，先确认候选再替换dist |
| `scripts/workflow.py` | 人工改动计划、测试/浏览器验收、准备与线上核验 | 浏览器通过后再同步；新对话使用现有命令 |
| `scripts/nightly.py` | 客户端判态、顺序采集、调用同一构建器、发布需要与回执 | 未登录由代码直接跳过；不另写构建或同步实现 |

`release_reuse.py` 暂保留旧输入/哈希函数的导入别名，便于既有脚本接续；这些别名没有第二份实现。新调用直接导入对应职责模块。

## 输入与生成物

数据指纹只依赖生成数据的算法、数据库内容、名单/排除配置、原始输入与北京时间自然周。`workflow.py`、同步器、浏览器测试等维护逻辑改变会使**验收回执失效**，但不因此重算战绩。调整输入定义本身会安全地让数据缓存失效一次。

前端指纹覆盖源码、依赖/运行时及实际页面资源。分享JS从 `lib/*.ts` 生成，属于前端产物；源码稳定性检测读取其源文件，避免把构建自己的正常写入误当成并发改源码。完整分片和摘要仍分开，不能互作输入。

数据、前端与验收指纹集中在一处维护；业务规则、冻结基准、公开白名单及原全部数据门禁保持原入口。

## 两种身份

- `build_id`：数据快照身份，公开manifest、档案/战报索引用它关联数据。同一份数据只改CSS时，它可以保持不变。
- `artifact_sha256`：完整发布目录的内容身份，包含相对文件名与每个文件SHA256。构建器、同步器和夜间发布判断使用同一个值；人工回执中的dist/release摘要采用同一算法。

产物摘要只存私有构建回执，不写入被摘要覆盖的公开manifest，避免自引用。发布成功并实际线上核验后，`nightly.py --mark-published` 复核本机目录并记录数据身份与产物身份。旧状态没有产物摘要时不会凭数据ID猜测前端一致；下一次实际发布验收后自然补齐。

## 完整性与复用

一次操作在 `release.lock` 内读取源清单。浏览器前后仍验证产物稳定；同步复用刚读出的源清单，只写变化文件，最后返回完整目标内容核对结果。构建器不再追加一个重复同步检查，人工流程也不再把同一目标紧接着完整读取两次。

这不是跨构建的mtime缓存。后续 `ready`、独立 `sync_release.py --check` 和线上验收仍重新读取当前内容；相同大小/时间的损坏文件也必须被识别。同步失败不提供可发布回执，可能已经部分更新的本机发布目录须修复并重新准备；线上旧站不会因为本机同步而自动改变。

## 继续维护

修改/测试/发布只按 [WORKFLOW](WORKFLOW.md)。在对应职责模块改动，增加可观察行为的回归；新增阶段同时更新依赖声明和阶段计时。避免增加第二套评分、第二套同步、通用插件框架或自动猜测身份/路径的回退。历史目录名沿用，当前事实只写STATUS，逐次证据写CHANGELOG。
